# Отчёт по проекту «Прогнозно-аналитические системы» (черновик разделов 1–7)

> Черновик для переноса в `Проект_Бражкин_АА_ПАС.docx`. Раздел 1 обновлён: в проект добавлен пользователь «водитель», стек изменён. Числа взяты из фактического прогона системы 02.10.2026.

## 1 Выбор и обоснование предметной области (изменения к согласованной версии)

**Предметная область и показатель** не изменились: общедоступная зарядная инфраструктура электромобилей Швейцарии. Прогнозируемый показатель — почасовая доля занятых точек Occupied / (Available + Occupied) по кантонам и классам мощности на 1–24 ч.

**Пользователи.** К аналитику по планированию инфраструктуры и инженеру данных добавлен **водитель электромобиля**. Для него система рассчитывает производный прогноз: вероятность того, что зарядная точка будет свободна через 5–60 мин, к моменту приезда. По этому прогнозу система рекомендует станцию с учётом совместимости разъёма и мощности автомобиля. Практическая задача расширена: результаты прогноза используются не только для планирования сети, но и для выбора станции в момент поездки.

**Источники данных.** К трём источникам из Таблицы 1.1 добавлены:
- открытый архив 5-минутных статусов 2022–2025 гг. (Swiss-public-charging-dataset, первоисточник BFE; Parquet в архивах 7z);
- справочник почтовых индексов swisstopo (CSV);
- каталог электромобилей Open EV Data (JSON).

Архив решает главную проблему исходного плана: источник статусов не хранит истории, а непрерывный сбор на учебном ПК невозможен. Теперь модели обучаются на двух годах истории, а текущий статус запрашивается в момент поиска.

**Технологический стек (вместо п. 1.5).**
- PostgreSQL 17: основная БД со слоями stg, core, mart, ops, ограничениями целостности, функциями, процедурами, триггерами и ролями. Запускается в Docker одной командой.
- DuckDB + Parquet: обработка архива (около 3 млрд строк за 2024–2025 гг.), в PostgreSQL записываются только агрегаты.
- FastAPI + Leaflet + Plotly: веб-приложение водителя и два дашборда. Metabase не используется, чтобы не поднимать второй сервер и не ставить плагин DuckDB.
- scikit-learn и LightGBM: модели прогноза.
- pytest, ruff, GitHub Actions: проверка при каждом изменении.

Репозиторий: https://github.com/yandhi2018/ev-charge-advisor-ch.

### 2.2 Особенности и проблемы данных, выявленные при разведке

1. **Смена идентификаторов.** Формат EvseID у некоторых операторов изменился (Swisscharge: `CH*SWIEE113532` в 2024 г. → `CH*SWI*E10662` в 2025 г.). С текущим справочником совпадает только 33 % точек июня 2024 г. и 45 % точек июня 2025 г. Метаданные из ChargingStationDetails (февраль 2026 г.) восстанавливают кантон и класс мощности для 67 % точек 2025 г. Поэтому модель B обучена на 2025 г., а признаки модели не зависят от конкретного идентификатора точки.
2. **Полнота архива.** 2024-12 в источнике пуст, 2024-10 неполный. Метки времени смещены на ±2 с и выравниваются по 5-минутной сетке. Месяцы 2025 г. весят меньше 2024-х при большем числе строк — это эффект сжатия, а не потеря данных.
3. **Статус Unknown** занимает около 18 % наблюдений 2025 г. Он не входит в знаменатель показателя и учитывается отдельно.
4. **Ошибки паспорта:** 158 записей одного оператора с координатами-заглушками (50, −15), 5 дублей EvseID, около 1 200 точек без мощности, 525 записей без типа тока.

## 3 Решения по обработке данных

### 3.1 Слоистая архитектура

| Слой | Хранение | Ответственность |
|---|---|---|
| raw | Файлы `data/raw/`, реестр `ops.raw_manifest` (путь, sha256, запуск) | Неизменяемая копия ответа источника; позволяет переобработать данные |
| staging | `stg.*`, `data/lake/stg/status_5min` | Приведение типов, единые коды, выравнивание времени, дедупликация |
| core | `core.*`, `data/lake/core/status_episode` | Справочники, разрешение сущностей, SCD2-история точек, погода, снимки статусов |
| mart | `mart.*` | Почасовая загрузка, профили доступности, прогнозы, метрики, полнота архива |
| ops | `ops.*` | Журнал загрузок, версии схемы, структуры источников, качество, карантин, lineage, реестр моделей |

### 3.2 Загрузка: инкрементальность, идемпотентность, устойчивость

Для каждого источника определены порция догрузки и ключ идемпотентности: см. README, раздел «Свойства загрузки».

Общие механизмы:
- повторы с экспоненциальной паузой и учётом HTTP 429 / Retry-After;
- атомарная запись файлов;
- журнал `ops.load_run`: строка создаётся в начале запуска, поэтому на неё могут ссылаться записанные данные;
- восстановление после аварийного завершения: зависшие запуски помечаются `failed`;
- частичный успех (`partial`) при сбое одного кантона или месяца.

При обработке архива нехватка памяти обрабатывается разбиением месяца на 16 частей по хэшу EvseID и повторной попыткой.

### 3.3 Дедупликация и разрешение сущностей

- Дубли EvseID в выгрузке: остаётся самая свежая запись по lastUpdate, число дублей фиксируется в журнале.
- Станция: поле ChargingPoolID у источника пустое, поэтому станция = точки одного оператора с одинаковым нормализованным адресом (ключ `core.fn_station_key`). Без адреса используются координаты, округлённые до ~10 м. Итог: 17 044 точки → 5 794 станции. Проверка `uniqueness_station_location` находит возможные дубли станций ближе 30 м.
- Кантон станции: по почтовому индексу (справочник swisstopo), иначе по ближайшему населённому пункту. Без кантона осталась 1 станция.

### 3.4 Справочники и историзация

Справочники: кантоны, индексы, операторы, типы разъёмов с таблицей сопоставления названий источников (OICP и каталога ЭМ), автомобили. История точек ведётся по SCD2: процедура сравнивает хэш значимых полей, триггер закрывает старую версию и открывает новую. Уникальный частичный индекс гарантирует одну открытую версию. Изменение служебных полей (last_seen) версию не порождает.

### 3.5 Управление изменением схемы

- Схема БД задаётся идемпотентными скриптами `db/00–07`; изменения существующих таблиц оформляются миграциями `db/migrations`.
- Каждая применённая версия файла фиксируется в `ops.schema_version` с контрольной суммой.
- Изменение структуры полей источника фиксируется в `ops.source_schema` и показывается на операционном дашборде.

### 3.6 Модель витрины

Основная витрина `mart.occupancy_hourly` имеет зерно «кантон × класс мощности × час». В ней хранятся средние числа свободных, занятых, неисправных и неизвестных точек, загрузка, доля неисправных и число наблюдённых 5-минутных слотов (полнота часа). Профили `mart.profile_group` и `mart.evse_profile` содержат долю времени, когда точка свободна, по дню недели и часу. Витрины прогнозов и метрик хранят результаты каждого фолда.

## 4 Аналитика

Предметный дашборд (`/analytics`, роль аналитика). Каждый элемент отвечает на один вопрос:

| Элемент | Вопрос |
|---|---|
| Рейтинг кантонов по загрузке AC и DC | Где сеть загружена сильнее всего? |
| Тепловая карта «день недели × час» | Когда пики? |
| Факт и прогноз на 6 ч | Насколько точен прогноз на ближайшие часы? |
| Загрузка по интервалам температуры | Влияет ли погода? |
| Доля неисправных точек по кантонам | Где неисправности мешают спросу? |
| Таблицы метрик моделей и бэктеста | Можно ли доверять прогнозу и рекомендациям? |

Фильтры: период, кантон, класс мощности.

Операционный дашборд (`/operations`, роль инженера) отвечает на вопросы:
- успешны ли последние загрузки и насколько свежи данные (по каждому источнику относительно допустимого возраста);
- нет ли аномалий объёма;
- где дыры в истории;
- какие проверки качества не пройдены;
- менял ли источник формат;
- как меняется сеть (SCD2) и что ушло в карантин;
- не деградировала ли модель (диаграмма надёжности).

Фильтры: период, источник, уровень проверок. Оба дашборда читают витрины при каждом открытии страницы, поэтому обновляются автоматически.

## 5 Модели и результаты валидации

### 5.1 Прогноз A: почасовая загрузка по кантонам на 1–24 ч

**Постановка.** Цель — загрузка y = Occupied / (Available + Occupied) для 52 рядов (26 кантонов × 2 класса мощности) в час t0 + h, h ∈ {1, 2, 3, 6, 12, 24}. Моменты прогноза t0 взяты каждые 6 ч. Часы, в которых наблюдалось меньше половины 5-минутных слотов, исключены.

**Признаки** известны в момент t0:
- значения ряда в t0, t0 − 1, t0 − 2 и среднее за 24 ч;
- значения y(t − 24 ч) и y(t − 168 ч) относительно целевого часа: при h ≤ 24 они лежат до t0;
- исторический профиль «кантон × класс × день недели × час», посчитанный только по обучающему окну;
- горизонт, час и день недели по местному времени, выходной, праздник кантона;
- погода на целевой час.

**Модели:**
- A0 — сезонная наивная модель (значение неделю назад), базовая;
- A1 — исторический профиль;
- A2 — глобальная модель LightGBM для всех рядов с горизонтом как признаком.

**Валидация** — rolling origin с расширяющимся окном, три фолда с зазором 7 дней между обучением и тестом: тест 06–07.2025, 08–09.2025 и 10–12.2025.

Меры против утечек:
- признаки не используют значения после t0;
- профиль считается в каждом фолде заново по его обучающему окну;
- ранняя остановка LightGBM идёт по последним 28 дням обучающего окна;
- на тесте используется архивный прогноз погоды Open-Meteo (то, что было известно заранее), а не фактическая погода.

Таблица 5.1 — Ошибка прогноза загрузки на тесте, п.п. загрузки

| Модель | Фолд 1 MAE | Фолд 2 MAE | Фолд 3 MAE | Среднее MAE | Среднее RMSE | MASE |
|---|---|---|---|---|---|---|
| A0 неделю назад (база) | 3,12 | 2,95 | 3,75 | 3,27 | 5,18 | 1,000 |
| A1 профиль | 3,14 | 3,03 | 4,39 | 3,52 | 5,14 | 1,068 |
| **A2 LightGBM** | **2,09** | **2,02** | **2,75** | **2,29** | **3,78** | **0,696** |

| Срез | A0 | A2 |
|---|---|---|
| h = 1 ч | 3,24 | 1,62 |

**Интерпретация.**
- LightGBM ошибается в среднем на 2,3 п.п. загрузки, на 30 % меньше базовой модели (MASE 0,70). Для кантона с 200 точками это ошибка примерно в 4–5 занятых точек.
- Преимущество наибольшее на коротком горизонте: на 1 ч ошибка вдвое меньше базовой. С ростом горизонта ошибка приближается к профилю, потому что вклад текущего состояния затухает.
- Быстрая зарядка (DC) прогнозируется хуже: точек меньше, ряды шумнее.
- Фолд 3 (октябрь–декабрь) сложнее остальных: праздничный сезон и рост доли статуса Unknown в декабре до 24 %.
- Профиль A1 без текущего состояния хуже наивной модели. Загрузка заметно меняется от недели к неделе, и «как неделю назад» точнее «как в среднем».

**Влияние погоды.** Если подставить на тесте фактическую погоду вместо архивного прогноза, MAE A2 не меняется (2,29 п.п.). Значит, погода почти не добавляет информации сверх календаря и лагов, а оптимизма от использования фактической погоды нет. Погода сохранена как признак: она нужна для предупреждения водителю о снижении мощности DC-зарядки в мороз.

## 6 Компоненты профиля «Управление данными»

**Контроль качества данных.** Каталог `config/dq_checks.yaml` содержит 18 проверок всех семи требуемых типов: полнота, уникальность, допустимость, типы, диапазоны, ссылочная целостность, актуальность. Результаты каждого прогона сохраняются в `ops.dq_result`.

Поведение при обнаружении некорректных данных:
- на этапе загрузки запись не допускается в core и уходит в `ops.quarantine` с причиной;
- нарушение проверки уровня error останавливает обновление витрин и обучение;
- нарушение уровня warn фиксируется и показывается инженеру.

**Метаданные и происхождение.**
- Граф `config/lineage.yaml` загружается в `ops.lineage_node` / `ops.lineage_edge`. Страница `/lineage` строит цепочку «источник → загрузка → raw → преобразование → слой → витрина → показатель → дашборд» рекурсивным запросом и связывает её с последним фактическим запуском загрузчика (run_id, время, путь к raw-файлу).
- Каждая строка данных хранит run_id запуска, а каждый raw-файл — sha256.
- Словарь данных генерируется из каталога PostgreSQL (`evadvisor docs`).

**Историзация.**
- SCD2-история зарядных точек (`core.evse_history`);
- история архивных прогнозов погоды (вид `hist_forecast` хранится отдельно от факта);
- журнал версий схемы и структур источников.

**Собственный компонент — рекомендатель станций.** Он использует серверную функцию подбора совместимых точек, модель B и журнал запросов с огрублёнными координатами. Эффект измерен бэктестом (раздел 5).

## 7 Технологическое исполнение

- **Воспроизводимость:** развёртывание по README тремя командами; база создаётся из скриптов без ошибок, в том числе повторно (проверяется в CI).
- **Автоматизация:** `evadvisor run-all` выполняет полный цикл; задача Планировщика Windows запускается ежедневно и догоняет пропуски после выключения ПК.
- **Конфигурируемость:** `config/*.yaml` и `.env`.
- **Открытость данных:** все источники общедоступны, персональные данные не собираются.
- **Качество кода:** 34 автоматических теста, линтер, CI на GitHub Actions.
